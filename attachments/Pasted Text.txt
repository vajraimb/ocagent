# 用 OCaml Effect 构建 Agent 及其 Harness：讨论与实施 Spec v0.1

**关于这次结果的说明：** 这次多模型调用没有返回各个模型各自的结论，只返回了检索资料和你的项目记忆。所以下面没有"哪些模型同意、哪些不同意"的对比表，凭空编一张会误导你。下面的判断由我综合 OCaml 官方文档、Eio、Temporal 等资料得出，并对照了你的 BRIGADE、YiState 和 effect runtime 项目。

## 一、结论

方向是对的。"Effect 定义能力，Handler 实现环境"适合用来拆掉 Harness 里的胶水代码。但原文有一处根本错误，另有三处说得过满，写进 spec 之前要先改掉。

### 1. 根本错误：原生 continuation 不能持久化

原文第 3 点说"Handler 直接持久化 continuation，响应到达后 `continue k` 恢复"。在 OCaml 5 里这做不到：

- continuation 是堆上的一个对象，指向一段运行时栈（fiber）。捕获它时不复制栈帧，所以它不是可以序列化的普通数据。
- `Marshal` 遇到函数值会失败，除非打开 `Closures` 标志；即使打开，也只能在同一个二进制里读回，处理不了运行时栈段。
- continuation 只能恢复一次（one-shot）。第二次恢复会抛 `Continuation_already_resumed`，所以也不能"留一份备份"。

因此 `continue k` 只适用于**进程还在**的短暂挂起，比如等几秒的审批或回调。**跨重启**的 durable execution 必须换一种做法：把每次 effect 的结果写进日志，重启后从头重放（event-sourced replay）。Temporal 就是这样做的：恢复时不还原内存快照，而是从头重跑 workflow，用记录下来的结果把代码带回原来的位置。

好消息是，effect 做重放比命令式代码自然得多。只需要一个 Replay handler：日志里已有的 effect 直接返回记录的结果，没有的才真正执行。Agent 代码完全不用改。原文想要的"无需编写状态重构逻辑"，靠重放就能实现，只是理由不是"持久化 k"。

### 2. 说得过满：没有静态的 effect 安全

OCaml 编译器不检查每个 effect 是否都有 handler。漏装一个 handler，要到运行时、执行到那个 `perform` 时才抛 `Effect.Unhandled`。所以"一键切换 Dev / Eval / Prod"需要两个配套措施：

- 每个 profile 都要有一个覆盖全部 effect 的 CI 测试。
- 在最外层放一个兜底 handler，把 `Unhandled` 转成带类型的错误。

更强的静态保证可以看 Jane Street 的 `handled_effect`，但它依赖 OxCaml。

### 3. 说得过满：Eio 的 fork 会"丢"你的 handler

这一点需要实测确认。Eio 的子 fiber 由底层调度器运行，你在 fork 点之上安装的 handler 很可能不在子 fiber 的栈里。Ocsigen 也遇到过类似问题：从回调里 `perform` 直接得到 `Unhandled`。

多 Agent、swarm 场景下必须规定：**每个子 fiber 入口都重新安装 Harness 栈**（用 `Harness.spawn` 封装）。M0 阶段要写一个测试，先证实或排除这个问题。

### 4. 说得过满："静默纠错"的方向不对

校验没通过时，不应该悄悄改掉返回给模型的内容。应该返回带结构的诊断信息，写进日志，并设重试上限。否则 Eval 无法复现，审计也说不清。这和你在 YiState 里"证据必须可追溯"的原则一致。

## 二、实施 Spec：`ocagent-harness` v0.1

### 2.1 目标与非目标

**目标：**
- Agent 核心代码只使用 `perform`，不直接依赖任何 SDK。
- 同一份 agent 代码可以跑在三种 profile 下：Dev、Eval（确定性、可重放）、Prod。
- 进程崩溃或重启后，靠重放恢复到断点，不重复执行已经完成的副作用。
- 审批、预算、校验、追踪都以 handler 的形式插拔。

**非目标（v0.1 不做）：**
- 多次恢复的 continuation（multi-shot）。
- 跨语言序列化 continuation。
- 分布式调度。后续可以接 BRIGADE 或 Temporal。

### 2.2 Effect 协议（`lib/proto/effects.ml`）

原文的 `string * string` 太弱，这里改成带类型的结构，并把所有不确定的来源都做成 effect：

```ocaml
type tool_call   = { call_id : string; name : string; args : Yojson.Safe.t }
type tool_result = { ok : bool; output : string; diagnostics : string list }
type approval    = { action : string; risk : [`Low | `High]; payload : Yojson.Safe.t }
type decision    = Approved | Rejected of string

type _ Effect.t +=
  | Llm         : Llm.request -> Llm.response Effect.t   (* 模型调用也是 effect，Eval 才能 mock/重放 *)
  | Tool        : tool_call -> tool_result Effect.t
  | Ask_human   : approval -> decision Effect.t
  | Checkpoint  : string -> unit Effect.t                (* 语义改为“日志屏障/fsync 点”，不是存 k *)
  | Compact     : Msg.t list -> Msg.t list Effect.t
  | Now         : float Effect.t                         (* 重放必须是确定的：时间、随机、ID 都走 effect *)
  | Fresh_id    : string Effect.t
```

**规则 R1：** agent 代码里禁止直接调用 `Unix.time`、`Random` 或任何 I/O。CI 用 grep 或 lint 拦截。

### 2.3 中间件写法

handler 先在请求前、结果后做自己的事；中间要真正执行时，在 handler 里再 `perform` 一次同一个 effect，这次会交给外层 handler 处理：

```ocaml
let with_budget ~max f =
  let used = ref 0 in
  Effect.Deep.try_with f ()
    { effc = fun (type a) (e : a Effect.t) -> match e with
      | Llm req -> Some (fun (k : (a, _) continuation) ->
          incr used;
          if !used > max then discontinue k Budget_exceeded
          else continue k (perform (Llm req)))     (* 转交外层 *)
      | _ -> None }
```

**嵌套顺序：** 写在最里层的 handler 最先拦截到 effect。规范的栈从内到外如下：

| 层（内 → 外） | 职责 | 备注 |
|---|---|---|
| `with_trace` | 记录 span 和日志 | 重放时打 `replayed=true` 标记，不重复上报 |
| `with_verify` | Tool 执行后跑 lint、测试、schema 校验 | 结果写进 `diagnostics`；同一 call_id 最多 N 次 |
| `with_budget` / `with_quota` | 统计次数和 token | 放在 Replay 以内，重放时预算状态会自然重建 |
| `with_policy` | 判断风险；`High` 级别转成 `Ask_human` | 规则是纯函数，可以复用 YiState 的门控 |
| `with_compact` | 超过阈值时调用 Llm 做摘要 | 摘要本身也是 Llm effect，会被记进日志 |
| **`with_journal_replay`** | 日志里有记录就直接返回，否则先执行、写入日志、fsync，再 `continue` | durable 的核心 |
| 执行层 | `with_sandbox`（Docker 或 mock）、`with_llm_client`、`with_human`（Slack/Telegram/CLI） | 只有这一层碰外部世界 |
| `with_strict` | 把 `Unhandled` 转成 `Harness_error` | 最外层兜底 |

### 2.4 Durable Execution：重放协议（替代"持久化 k"）

日志采用 JSONL 或 SQLite，每条记录如下：

```
{ run_id; seq; kind; req_hash; status: Done|Pending; result; ts }
```

replay handler 收到第 n 个 effect 时：

1. **日志里有第 n 条：** 先校验 `req_hash`。不一致就抛 `Nondeterminism`（类似 Temporal 的 DeterminismViolation）。一致就直接 `continue k recorded`。
2. **没有，且是普通副作用：** 先写 `Pending` 和幂等键，再执行，再写 `Done`，最后 `continue`。副作用至少执行一次，用幂等键防止重复。
3. **没有，且是 `Ask_human`：** 写 `Pending`，然后 `discontinue k Suspended`。调用栈会正常展开，`Fun.protect` 里登记的资源也会释放，进程可以退出。
4. **审批结果到达后：** 把结果写进第 n 条，重新运行 `agent prompt`，重放会一路快进到断点。
5. **等待时间很短（几秒）且进程不退出时：** 可以走快速路径，把 k 保存在内存里等待。关闭进程前必须对所有挂起的 k 调用 `discontinue`，否则它们持有的资源会泄漏。

**升级规则：** 修改 agent 代码会让旧日志的重放失效。`run_id` 要绑定 `agent_version`，跑在旧版本上的任务只能用旧二进制完成，或者显式迁移。

### 2.5 反馈闭环规范

`with_verify` 只拦截写入类工具（`write_file`、`apply_patch`），之后通过 `perform (Tool lint_call)` 调用校验器，所以校验结果也会记进日志。校验失败时返回：

```
{ ok = false; output; diagnostics = [...] }
```

由 agent 主循环决定是否重试，最多 3 次。handler 不替模型重写内容，只附加诊断信息。

### 2.6 Profile 组合（`lib/profiles.ml`）

```ocaml
let eval  = stack [strict; mock_world ~fixtures; journal_replay ~mem; budget 10; verify; eval_logger]
let prod  = stack [strict; docker_sandbox; llm_client; telegram_approval;
                   journal_replay ~sqlite; policy; budget; verify; otel_trace]
let run profile agent prompt = profile (fun () -> agent prompt)
```

`Harness.spawn`：子 agent fork 时，在子 fiber 内重新应用同一个 profile，并给子任务分配自己的 `run_id`。这和 BRIGADE 的 Switch 取消树是对齐的。

### 2.7 里程碑（按 PR 拆分）

| PR | 内容 | 验收 |
|---|---|---|
| M0 | 协议、`with_strict`，以及 Eio fork 继承 handler 的验证测试 | 证实或证伪第一节第 3 点；每个 profile 都通过 effect 覆盖测试 |
| M1 | Mock world、budget、eval logger | 同一 fixture 跑 100 次，日志逐字节一致 |
| M2 | journal 与重放 | 在任意 seq 位置 kill -9 后重启，结果一致，副作用不重复执行 |
| M3 | Ask_human 挂起与恢复（Telegram 通道） | 隔一天审批后可以恢复；`Nondeterminism` 测试会触发报错 |
| M4 | verify、policy（接入 YiState 门控）、compact | SWE 类小任务上，修复率和 token 消耗有对照数据 |
| M5 | Docker sandbox、OTel，接入 BRIGADE 做多 agent | swarm 任务中子 agent 崩溃，监督者收到 DOWN 后能重放恢复 |

## 三、修正后的对比表

| 维度 | 命令式 Harness | Effect Harness（修正版） |
|---|---|---|
| 中断与恢复 | 手写状态序列化 | **effect 结果日志 + 自动重放**；agent 代码保持不变，但要求确定性 |
| 环境切换 | 配置分支 | 组合 handler 栈，**需要 CI 覆盖测试**（没有静态保证） |
| 并发 | 回调或 async | 直写风格；**子 fiber 需要重新安装 handler** |
| 纠错 | 硬编码在主循环 | 由 handler 附加结构化诊断，交给 agent 决定，并写进日志 |

**下一步建议：** 先做 M0 和 M2。这两个最能证明这个架构可行：一个确认 Eio 下 handler 会不会丢，另一个验证重放加 kill -9 后能否正确恢复。需要的话，我可以按你习惯的方式，把 `with_journal_replay` 的完整实现逐行写出来讲解。
